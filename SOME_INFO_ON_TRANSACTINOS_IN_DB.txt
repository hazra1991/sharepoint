🧠 PostgreSQL Transactions & Row-Level Locks (Clean Version)
1. Every query is a transaction

Autocommit mode (default): Each query is automatically wrapped in a transaction:

BEGIN;
<your query>
COMMIT;

Manual transactions: You can explicitly start a transaction:

BEGIN;
-- run multiple queries
COMMIT;  -- or ROLLBACK on error

Failed transactions: If any query inside a transaction fails, PostgreSQL marks the transaction as aborted. All subsequent queries fail until you ROLLBACK.

Example: simple SELECT
SELECT * FROM sku;

Internally wrapped as:

BEGIN;
SELECT * FROM sku;
COMMIT;

Locking: none, because plain SELECT uses MVCC (reads last committed snapshot).

2. SELECT ... FOR UPDATE — row-level locking

Used to safely update a row in concurrent systems:

SELECT * FROM sku WHERE name='test_sku' FOR UPDATE;
Behavior:

Creates a row-level lock

Prevents other transactions from UPDATE or DELETE on the same row

Other SELECT queries are not blocked (MVCC)

Lock is held until transaction ends (COMMIT or ROLLBACK)

Other transactions attempting SELECT ... FOR UPDATE or UPDATE/DELETE on that row wait until lock is released.

Example: locking a row

Session 1:

BEGIN;
SELECT * FROM sku WHERE name='test_sku' FOR UPDATE;
-- row locked

Session 2 (concurrent):

UPDATE sku SET description='new desc' WHERE name='test_sku';
-- waits until Session 1 commits or rolls back
3. UPDATE or DELETE automatically acquire locks

Even without FOR UPDATE:

UPDATE sku SET description='updated';
DELETE FROM sku WHERE name='test_sku';

PostgreSQL locks affected rows automatically

Other transactions trying to update/delete the same rows will wait

Other plain SELECT queries are not blocked (MVCC)

Example:

Session 1:

BEGIN;
UPDATE sku SET description='temp' WHERE name='test_sku';
-- row is locked

Session 2:

UPDATE sku SET description='other' WHERE name='test_sku';
-- waits until Session 1 commits

Session 1 commits:

COMMIT;
-- Session 2 now proceeds
4. SELECT works under MVCC & isolation levels

PostgreSQL uses MVCC (Multi-Version Concurrency Control):

Readers do not block writers

Writers do not block readers

What a SELECT sees depends on the transaction isolation level:

Read Committed (default): sees last committed rows

Repeatable Read: sees snapshot at transaction start

Serializable: may abort if concurrent updates cause conflicts

Example:
-- Session 1
BEGIN;
UPDATE sku SET description='locked row' WHERE name='test_sku';
-- row locked

-- Session 2
SELECT * FROM sku WHERE name='test_sku';
-- returns old value (before update) due to MVCC
5. Summary Table
Operation	Lock?	Effect on other sessions
SELECT (plain)	No	Reads last committed snapshot
SELECT ... FOR UPDATE	Yes	Other updates/deletes wait
UPDATE / DELETE	Yes	Other updates/deletes on same row wait
Transaction fails inside session	N/A	Must rollback; subsequent queries fail

@transaction.atomic

        return False

    phone.save()

select_for_update() generates SELECT ... FOR UPDATE

Guarantees row-level lock until transaction ends

Prevents lost updates in concurrent systems

Normal queries (PhoneNumber.objects.get()) can still read the row

🧠 Transactions & Row-Level Locks in Relational Databases

Most modern relational databases (PostgreSQL, MySQL/InnoDB, Oracle, SQL Server) support transactions, row-level locks, and MVCC, but the behavior can vary slightly. Here’s a structured view:

1. Every statement is in a transaction

Implicit transaction: Many databases automatically wrap each statement in a transaction if you haven’t explicitly started one.

PostgreSQL → autocommit mode

MySQL (InnoDB) → autocommit by default

Oracle → does not auto-commit SELECT/UPDATE, explicit COMMIT required

Explicit transaction: You can control boundaries via:

BEGIN;
-- multiple queries
COMMIT;  -- or ROLLBACK

Failed transaction: Any error inside a transaction typically marks the transaction as aborted, requiring rollback before further queries.

2. Row-level locking

SELECT ... FOR UPDATE (or database equivalent) locks rows for updates or deletes:

DB	Locking behavior
PostgreSQL	Row locked until COMMIT; other updates wait
MySQL/InnoDB	Row locked; other updates wait; can use NOWAIT via LOCK IN SHARE MODE + extra logic
Oracle	Row locked for updates until COMMIT; readers are not blocked
SQL Server	Row-level locks by default for UPDATE; can escalate to page/table

Important: plain SELECT queries do not block updates (MVCC in PG/MySQL/InnoDB; read consistency in Oracle).

3. UPDATE or DELETE automatically acquire row locks

Updating or deleting a row in any ACID-compliant DB typically locks that row:

Scenario	Other sessions behavior
UPDATE row X	Other updates on X wait until COMMIT
DELETE row X	Other updates/deletes on X wait
SELECT row X	Usually not blocked; reads consistent snapshot
4. Transaction isolation levels

Isolation level determines what other transactions can see:

Isolation	Behavior
Read Committed	Sees only committed changes; uncommitted changes invisible
Repeatable Read	Sees snapshot at transaction start; prevents non-repeatable reads
Serializable	Highest isolation; may abort concurrent conflicting transactions

MVCC (multi-version concurrency control) ensures readers never block writers, and writers don’t block readers in most modern databases.

5. Why locking the “source of truth” row matters

Example: reservation system for unique numbers

If you lock the reservation table, two transactions could simultaneously check for a number → both see “free” → duplicate inserts.

If you lock the PhoneNumber row itself, there’s only one canonical row for that number:

Guarantees only one transaction can reserve/update at a time

Prevents race conditions

This principle applies to all relational databases that support row-level locking.

6. Key points across major DBs
Feature	PostgreSQL	MySQL/InnoDB	Oracle	SQL Server

SELECT ... FOR UPDATE	Row-level lock	Row-level lock	Row-level lock	Row-level lock
Row-level lock on UPDATE	✅	✅	✅	✅
SELECT blocks UPDATE?	❌ (MVCC)	❌ (MVCC)	❌	❌
